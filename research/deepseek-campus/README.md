# 校园 Soar 规则真实模型小样测试

使用用户指定的 `deepseek-v4-flash-vision-exp`，端点 `https://api.deepseek.com/chat/completions`。共 3 次补全请求，已停止；没有后台循环，也没有把密钥、模型调用或这些实验规则接入网页。

结论：第三次输出能在原生 Soar 中安装并执行，但未通过行为验收，不能直接用作正式人物策略。

## 测试范围

这是一个独立的 M/T 舞会邀请决策实验，使用现有 Soar 9.6.5 WASM、SMem、个人认知记录与存档功能。不是完成后的校园游戏运行记录。

M 喜欢 T，也在意朋友接纳。测试明确植入初始经历与相应结构化认知：M 主动与 T 私聊愉快，朋友直接对 M 表达了排斥；后来另一个被 M 感知的支持事件使其压力认知降低。这些是人为定义的实验输入，尚未测试模型从任意自然语言自动推导好感或压力。

决策输入从该人物的原生记忆读取。新增规则只提出候选 operator；共享规则根据优先级选出操作，测试适配器收取 output-link 命令。没有人工修改模型源代码来凑结果。

## 行为结果

| M 的情境 | 原生 Soar 实际选择 |
|---|---|
| 私下、压力低、T 邀请 | 接受舞会邀请 |
| 私下、压力高、T 邀请 | 请求私聊；已有私下场合，属于不合适的重复请求 |
| 公开、压力低、T 邀请 | 请求考虑时间 |
| 公开、压力高、T 邀请 | 请求考虑时间 |
| 其他人邀请 | 通用考虑时间策略；没有继承对 T 的好感 |
| 私聊候选不可用 | 通用考虑时间策略；不会输出不可用命令 |

12 项检查中 10 项通过，2 项未通过。通过项包括真实规则触发、同一输入移除规则后选择发生变化、对象绑定、人物记忆隔离、压力记忆更新后私下选择改变、好感保留、候选约束、原生存档恢复与零 API 复用。

未通过的行为要求：

1. 提示要求公开场合下压力变化影响取舍，但两种压力下所选行动完全相同；只改了规则名、优先级和理由。在这个实验中，没有其他竞争目标，优先级变化没有改变行为。
2. 已处于私下场合仍请求私聊。初版接口也过于宽松，允许该候选出现。正确的游戏适配器应排除它；排除后虽然能兜底，但并没有证明人物获得了合理的后续方案。

这些要求用于验收本次明确的生成任务，不意味着现实中每个人的每个压力变化都必须导致另一种行动。M 的长期动机、连续多轮协商、离开后重约、承诺及实际社交后果仍需在校园切片中验证。

## 复现

从项目根目录运行：

```bash
node scripts/check-campus-model.mjs
```

无需密钥，不会产生费用。脚本在原生内核重新编译全部返回，并运行第三次规则的对照实验，生成 `verification.json`。当前退出码为 1，表示行为验收未通过；报告中的 `acceptedForGame` 为 false。不要把这个结果改成全绿，或把语法通过表述为完整游戏通过。

本次说明真实调用链和原生执行链已经验证；没有证明该模型能稳定直接编写合格的任意 Soar 程序。下一步应使用固定可编译骨架、严格行动前置条件和行为对照验收，再测有限数量的新策略。
